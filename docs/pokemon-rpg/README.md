# Pokémon RPG — Diário de Treinador

- **Regras** (livro consolidado, v0.2): [`regras.md`](regras.md)
- **Código-fonte do site**: [`site/diario-de-treinador.html`](site/diario-de-treinador.html)
- **Site publicado**: veja a seção [Publicar no GitHub Pages](#publicar-no-github-pages-uma-vez) abaixo — depois de ativado, o link fica em `https://<seu-usuário>.github.io/<repositório>/`.

O site é uma página HTML única, hospedada de graça no **GitHub Pages**, com os dados (fichas de todo mundo) salvos em tempo real num banco **Firebase Firestore** (também grátis, sem cartão de crédito). Sem esse banco configurado, o site abre mas mostra uma tela avisando que falta ligar o banco de dados.

## Visual e sprites

O tema é mais "jogo" que "wiki": fundo em tom pergaminho, cantos arredondados, títulos numa fonte pixelada (Press Start 2P) e badges de Tipo em formato de pílula. Cada Pokémon na ficha mostra automaticamente o sprite pixelado oficial da espécie (via [PokeAPI/sprites](https://github.com/PokeAPI/sprites), puxado pelo número da Pokédex salvo quando a Espécie é preenchida) — sem espécie definida, mostra um "❔" no lugar.

## Regras e guias dentro do site

O botão **"📖 Regras"** (no topo, em qualquer tela) abre três sub-abas, cada uma buscando o `.md` correspondente direto deste repositório — não são cópias coladas no site:

- **📜 Regras** — [`regras.md`](regras.md), o livro de regras.
- **🎒 Guia do Treinador** — [`guia-treinador.md`](guia-treinador.md), passo a passo de uso pra quem joga: desde entrar/criar personagem até cada função da própria ficha (tema claro/escuro incluso).
- **🛠️ Guia do Mestre** — [`guia-mestre.md`](guia-mestre.md), o mesmo tipo de passo a passo, mas das funções exclusivas do Mestre.

Como nenhum desses é uma cópia colada no HTML: sempre que a gente atualizar qualquer um dos três arquivos e enviar o commit, a próxima vez que alguém abrir aquela aba no site já vê a versão nova, sem precisar tocar no código. **Toda função nova do site precisa ganhar uma explicação nesses guias** — ao contrário do livro de regras (que só existe pra descrever o sistema em si), os guias existem pra ensinar a usar o que já está em vigor no site, então não podem ficar desatualizados. Funciona antes mesmo de configurar o Firebase.

## Como usar o site

- **Mestre**: define um PIN na primeira vez que entrar em "Sou o Mestre"; depois disso, usa esse mesmo PIN pra sempre. Vê e edita a ficha de todos os Treinadores da mesa, incluindo Nível e Vínculo (que os jogadores só enxergam, não editam) e o contador de batalhas vencidas (visível só pro Mestre).
- **Treinador**: cria a própria ficha (nome + PIN) em "Sou Treinador → Criar personagem"; depois entra de novo com nome + PIN. Pode ativar "Compartilhar com a mesa" pra deixar outros Treinadores verem a própria ficha (somente leitura).

### Progressão de Nível

A cada 4 batalhas vencidas (contador que só o Mestre vê e mexe), o Treinador sobe 1 Nível automaticamente e o contador zera. Ver [`regras.md`](regras.md#24-progressão-de-nível) para detalhes.

## Configurar o banco de dados (Firebase) — uma vez só

1. Acesse [console.firebase.google.com](https://console.firebase.google.com/) e entre com uma conta Google.
2. **Criar projeto** → dê um nome qualquer (ex: `diario-de-treinador`) → pode desativar o Google Analytics → **Criar projeto**.
3. No menu lateral, vá em **Compilação → Firestore Database** → **Criar banco de dados** → escolha um local (qualquer um serve) → inicie em **modo de teste** (ajustamos as regras de acesso no passo 6).
4. Ainda no console, clique no ícone de engrenagem (⚙️) → **Configurações do projeto**. Na aba **Geral**, role até "Seus apps" → clique no ícone **`</>`** (Web) → dê um apelido ao app → **Registrar app**.
5. O Firebase vai mostrar um bloco `firebaseConfig` parecido com este:
   ```js
   const firebaseConfig = {
     apiKey: "AIzaSy...",
     authDomain: "diario-de-treinador.firebaseapp.com",
     projectId: "diario-de-treinador",
     storageBucket: "diario-de-treinador.appspot.com",
     messagingSenderId: "123456789",
     appId: "1:123456789:web:abcdef"
   };
   ```
   Copie esses 6 valores e cole-os no arquivo [`site/diario-de-treinador.html`](site/diario-de-treinador.html), substituindo o bloco `FIREBASE_CONFIG` no topo do `<script>` (procure por `COLE_AQUI`). Depois salve, faça commit e push.
6. **Regras de segurança do Firestore** — no console, vá em **Firestore Database → Regras** e cole exatamente isto (restringe leitura/escrita a só esse documento do jogo, e bloqueia qualquer outra coisa no banco):
   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /diario/estado {
         allow read, write: if true;
       }
       match /{document=**} {
         allow read, write: if false;
       }
     }
   }
   ```
   Clique em **Publicar**.

Pronto — depois disso, qualquer pessoa que abrir o site (em qualquer aparelho) lê e escreve no mesmo banco em tempo real: o que um jogador edita aparece pros outros sem precisar recarregar a página.

## Instalar como app (PC, Mac, Linux, Android)

O site já é um **PWA** (Progressive Web App) — dá pra "instalar" ele como se fosse um programa de verdade, com janela própria, ícone na área de trabalho/barra de tarefas e sem a barra de endereço do navegador, sem precisar baixar nem instalar nada separado:

1. Abra o link do Diário de Treinador (o de `.../pokemon-rpg/site/diario-de-treinador.html`) no **Chrome** ou **Edge**.
2. Clique no ícone de instalação que aparece do lado direito da barra de endereço (um monitor com uma setinha) — ou no menu **⋮ → Salvar e compartilhar → Instalar app "Diário de Treinador"**.
3. Pronto — abre uma janela própria, com a Pokébola como ícone, e um atalho fica salvo (Menu Iniciar/Launchpad/gaveta de apps, dependendo do sistema).

**Ele sempre mostra a versão mais nova do site — não é uma cópia.** A "instalação" só cria um atalho que abre a mesma página ao vivo, então qualquer atualização publicada aqui (Movimento corrigido, regra nova, o que for) já aparece sozinha na próxima vez que abrir o app — e os dados do jogo continuam sincronizando em tempo real pelo Firebase do jeito de sempre, exatamente como no navegador comum. Não tem passo de "atualizar o app": não existe uma versão separada pra atualizar.

Tecnicamente, isso é um `manifest.webmanifest` (nome, ícone, cor do tema) + um Service Worker mínimo (`sw.js`, só existe pra habilitar o botão "Instalar" — não guarda cache de nada, então nunca serve uma versão velha) — os dois arquivos moram do lado do `diario-de-treinador.html`, dentro de `pokemon-rpg/site/`.

## Sincronização entre aparelhos

Sim: os dados do jogo (fichas, PINs, Vínculo, Nível, batalhas etc.) ficam salvos no Firebase, não no navegador — então editar no celular aparece no PC e vice-versa, em tempo real. Só duas coisas ficam presas a cada aparelho, por conveniência, e nunca afetam os dados do jogo: se você está logado (pra não pedir PIN toda hora) e quais fichas estão abertas/fechadas na tela.

## Segurança

Os PINs ficam guardados em texto simples no banco de dados. É uma trava social para o grupo, não um cofre: alguém com acesso técnico ao banco (ou ao link, se as regras de segurança não estiverem configuradas como acima) consegue ver os dados de todo mundo. Não reutilize senhas importantes como PIN aqui.

## Quem edita o quê

- **Mestre**: quem "coloca o Pokémon na ficha" — Espécie, Tipo 1/2, Atributos Naturais e os 4 Movimentos de qualquer Treinador da mesa, além de adicionar/remover Pokémon do time de alguém. Também é o único que edita Estágios e PP (Atual/Máximo) diretamente.
- **Treinador**: cuida do dia a dia da própria ficha — Apelido, PV atual, Condição/Confuso, e **reorganizar os próprios Pokémon** entre Equipe e Banco (ver abaixo). Estágios e PP mudam sozinhos pelo sistema (Movimento usado, item, saída de campo), sem edição direta do jogador. Não escolhe qual Pokémon entra na ficha — isso é só do Mestre.

## Pokédex completa (Gen 1–9) e banco de Movimentos

O site já vem com **todos os 1025 Pokémon** (espécie base de cada um, sem formas regionais/Mega/Gigantamax) e **847 Movimentos oficiais** embutidos — tipos, categoria e Base Stats/Poder/Precisão/Prioridade/**PP** reais, convertidos pelas tabelas das regras (Cap. 6.1 para Atributos, Cap. 9 para Poder de Movimento, Cap. 8.6 para PP). Fonte dos dados: [PokeAPI](https://pokeapi.co/).

- **Espécie** (só o Mestre vê o campo): digite o nome em inglês, como no jogo — assim que bater com um da base, Tipo 1/2 e os seis Atributos Naturais são preenchidos sozinhos, sem precisar clicar em nada.
- **Movimentos, Mestre**: campo "nome" livre com autocomplete, sem restrição (pode digitar qualquer um dos 847) — preenche Tipo/Categoria/Poder/Precisão/Prioridade/Efeito sozinho e continua editável na mão. Movimentos de poder fixo/variável (Seismic Toss, Dragon Rage, Counter, etc.) ficam com Poder em branco — é regra em aberto (Cap. 25), o Mestre adjudica na hora.
- **Movimentos, Treinador**: escolhe os próprios 4 Movimentos, mas restrito ao que a espécie realmente pode aprender — uma barra "Learnset" horizontal por slot, acima da mini-tabela dele, com quatro opções (**Nível** = aprendizado natural, só até o teto liberado pelo Nível do Treinador (Cap. 8.2/8.4); **Evo** = ganho ao evoluir pra essa forma; **TM** = só o que a espécie aprende por Fita, sem depender de Nível; **Egg** = só o que a espécie aprende por Breeding). Os dados de aprendizado (learnset) também vêm do PokeAPI. Não existe opção de HM — a mecânica saiu dos jogos oficiais a partir da Geração 9.
- Z-Moves e Movimentos Dynamax/Gigantamax **não** estão na base — são mecânicas de spin-off sem regra equivalente neste sistema.

## Equipe e Banco (arrastar Pokémon)

Cada Treinador tem 6 posições de **Equipe** (os Pokémon ativos) e um **Banco** sem limite (menu deslizante — botão "🗃️ Banco (N)" abre/fecha). O próprio Treinador (ou o Mestre) reorganiza arrastando pela alcinha **⠿** no canto do card — só isso: quem decide qual Pokémon existe e o que ele é continua sendo o Mestre.

- Arraste um Pokémon do Banco pra um slot vazio da Equipe → ele entra no time.
- Arraste um Pokémon do Banco pra cima de um Pokémon já ativo → eles trocam de lugar (o ativo vai pro Banco).
- Arraste dentro da própria Equipe (ou dentro do próprio Banco) → troca as posições dos dois.
- Arraste um Pokémon ativo pra dentro do Banco (área vazia do menu) → ele sai da Equipe e vai pro Banco.

Funciona com mouse e com toque (celular).

## Arena (esboço v1 + motor de ataque)

Botão **"🏟️ Arena"** no topo — espaço à parte pra montar uma batalha, feito como primeiro rascunho pra iterar em cima. Modelo de dados novo em `STATE.arena` (`teams` + `entries` + `lastRoll` + `log` + `round`), migração automática pra fichas salvas antes disso existir.

- **Times**: sem limite, criados/renomeados/removidos só pelo Mestre — não precisa ser 1×1, dá pra ter quantos Times a mesa quiser.
- Cada Treinador arrasta (pelo ⠿, mesma engine de Pointer Events da Equipe/Banco) um Pokémon da própria Equipe ativa pra dentro de um Time. A entrada guarda só a referência (Treinador + Pokémon) — o Pokémon continua na ficha normalmente, nada é duplicado ou movido de lá.
- **Equipe ativa é pública, mas cada Pokémon começa em Pokébola**: `arenaSourceHTML()` renderiza o card "Equipe ativa" de **todos** os Treinadores (`STATE.trainers.map(arenaTrainerSourceHTML)`) pra qualquer viewer, jogador ou Mestre — os cards de todo mundo aparecem sempre. Mas cada Pokémon nele só mostra sprite/nome de verdade pra quem for `canControl` (dono ou `SESSION.role==='gm'`) OU já tiver `p.arenaRevelado===true`; pra qualquer outro viewer, vira um tile Pokébola (`arena-source-tile-hidden`) até o Pokémon ir pra um Time pela primeira vez. Controle (`drag-handle`, `arena-source-tile-swappable`) segue restrito a `canControl` do mesmo jeito.
- **Dentro de um Time, revelado é `true` por padrão** (`DT.arenaSetEntry`/arrastar, `DT.arenaSwapIn`/Trocar): um Pokémon aparece pra mesa inteira (sprite, `arenaEntryHTML`) assim que entra por esses dois caminhos, mesmo antes de agir — persistido no próprio Pokémon (`p.arenaRevelado`), então mesmo saindo do Time depois, ele já aparece de verdade na Equipe ativa dali em diante, **pelo resto dessa mesma passagem pela Arena** (`p.arenaRevelado` zera ao sair de vez — `DT.arenaLeave` — ver bullet abaixo; sem esse reset, um Pokémon que já lutou uma vez ficava marcado como revelado pra sempre, vazando o roster inteiro do Treinador em toda Soltura futura). **Exceção**: uma entrada criada por `DT.arenaPickLead` (Soltura, ver bullet dedicado abaixo) nasce com `revelado:false` de propósito — fica em Pokébola até `DT.arenaRevelarTodos`. `migrateState()` **não** força mais essas a `true` (removida a migração antiga que fazia isso — ela existia de quando toda entrada nascia revelada; hoje `revelado:false` é um estado normal e esperado).
- **Motor de turno reescrito (Cap. 86): seleção simultânea + resolução manual em lote por Iniciativa**, substitui de vez a fila sequencial "um de cada vez" + a negociação de Prioridade (ambas removidas — ver "O que ficou pra trás" mais abaixo). `STATE.arena.round` agora é `{number, phase:'selecting'|'resolving', order, meta, actions, resolveOrder, resolveIdx}` — só o Mestre inicia (`DT.arenaStartRound`, "▶️ Iniciar Batalha", calcula `order`/`meta` com `computeInitiativeOrder()`, mesmo critério de sempre: Velocidade Efetiva → Natural → 1d6 em empate, −10 de Paralisia do Cap. 20.4, excluindo `revelado:false`). Na fase `'selecting'`, **todo mundo escolhe a própria ação livremente e ao mesmo tempo** — `DT.arenaSelectActor` libera qualquer entrada que ainda não tenha uma ação registrada em `round.actions` (`arenaEntriesPendingSelection`), sem depender de "vez" nenhuma; o Mestre pode escolher por qualquer uma que ainda não escolheu (nunca reabre uma já escolhida, nem ele). **Cap. 80 — trava real**: sem `STATE.arena.round` ou fora da fase `'selecting'` (antes de "Iniciar Batalha", ou já resolvendo), **ninguém** abre o menu de ação — nem o Mestre; a única oportunidade de agir é durante a seleção de uma Rodada de verdade. Cada escolha (`arenaQueueAction`) só grava o *bundle* da ação (`{kind:'atacar'|'item'|'trocar'|'fugir', ...}`) em `round.actions[entryId]` — nada resolve ainda. Assim que `arenaEntriesPendingSelection(round).length===0` (todo mundo que podia escolher já escolheu), a Rodada passa sozinha pra `'resolving'` (`arenaBeginResolving`); o Mestre também pode forçar isso antes (`DT.arenaForceResolve`, "Resolver Rodada", pra quando alguém sumiu/travou e a auto-resolução nunca ia disparar). `arenaComputeResolveOrder(round)` decide a ordem de resolução: **ações que não são Ataque (Trocar/Item/Fugir) sempre resolvem primeiro** (entre elas, por Velocidade Efetiva — critério estável), **depois** os Ataques, ordenados por Prioridade desc. → Velocidade Efetiva desc. → Velocidade Natural desc. → 1d6 em empate total (`resolveInitiativeTies`) — sem perguntar nada a ninguém: Prioridade simplesmente entra na frente. **Resolução 100% manual (revisado depois do Cap. 86 original, a pedido do usuário — "eu quero que seja manual... o mestre vai avançando de momento em momento")**: `arenaResolveNextStep(round)` executa **um** passo pendente por vez (`arenaExecuteQueuedAction` despacha pro tipo certo — `arenaExecuteQueuedAttack`/`Item`/`Swap`/`Flee`, rodando os mesmos testes de Paralisia/Sono/Congelamento (Cap. 20.4/21/22) e Confusão (Cap. 23) de sempre, só que agora na hora de RESOLVER, não de escolher — isso é o que permite Usar Item pra curar a própria condição bloqueante ANTES do teste obrigatório, Cap. 82: quem escolheu Item nunca passa por esse teste, e Item sempre resolve antes de qualquer Ataque), mas só quando o Mestre chama — não existe timer nenhum agendando o próximo passo sozinho. `DT.arenaResolveStep` (botão **"▶️ Avançar"** no card "🎯 Iniciativa", só GM) chama `arenaResolveNextStep` uma vez por clique, com a mesma trava de sempre contra o dado ainda animando/popup de Ação congelado (`if(SESSION.arenaResolving || DICE_ROLL_ANIM) return;`, Cap. 79) — não deixa adiantar o próximo Pokémon antes do resultado atual assentar na tela de todo mundo. **Não existe mais nenhum ticker** (`ensureRoundResolveTicker`/`checkArenaRoundResolution`/`ROUND_RESOLVE_GAP_MS`/`round.nextStepAt` — todos removidos de vez; a versão original deste capítulo tinha um `setInterval` de 300ms avançando sozinho a cada 3s, substituído por esse clique manual). Quando o `resolveOrder` inteiro termina, `arenaFinishRoundResolution` já monta a Rodada seguinte sozinha, de volta em `'selecting'` (`arenaBuildSelectingRound` — quem estiver `carregando` um Movimento de 2 turnos já nasce com a ação de soltar PRÉ-escolhida ali, sem passar pela seleção de novo) — só precisa "Iniciar Batalha" uma vez; com a batalha já vencida, a Rodada simplesmente termina (`STATE.arena.round=null`) sem abrir outra. Um Pokémon que entra de surpresa numa Rodada já em andamento (Mestre mandando alguém novo pro Time) **não** é mais inserido nela — a antiga regra do Cap. 16 original de "pular a frente de quem ainda não agiu" foi **aposentada** (a fila sequencial que ela dependia não existe mais); ele só participa normalmente a partir da próxima fase de seleção. Uma troca voluntária (Trocar como ação) continua consumindo a ação inteira; o convite de graça pós-U-turn/Volt Switch/Parting Shot ou pós-desmaio (`entry.pendingSwitchOut`/fainted-swap) agora **nunca expira sozinho** — fica disponível (clicável) até alguém de fato trocar, mesmo depois da Rodada virar, já que a resolução em lote não dá mais pra pausar no meio esperando um clique só.
- **Bug real corrigido nesta leva: `arenaCheckVictory` "esquecia" um Time inteiro quando um Treinador tinha entradas em dois Times diferentes** (o Mestre pode arrastar Pokémon do mesmo Treinador pra Times separados na mão) — o cálculo antigo colapsava `trainerId->teamId` num mapa (`teamOfTrainer`), sobrescrevendo pela ÚLTIMA entrada de cada Treinador; se esse Treinador também tivesse uma entrada mais antiga num Time diferente ainda vivo, esse Time desaparecia do cálculo de "quem ainda tem alguém vivo" e podia decretar o Time errado como vencedor. Corrigido pra computar `teamsAlive` direto por entrada (`e.teamId`, sem colapsar), então cada Time é conferido pela vida do Treinador de cada entrada dele, sem apagar um Time por causa de outra entrada do mesmo Treinador em Time diferente.
- **Ação de verdade — clicar no Pokémon, sem botões separados**: não existe mais "Usar" nem "Atacar"/"Agir" como botões próprios — clicar direto no card de um Pokémon num Time (já visível desde que entrou lá) e vivo (`DT.arenaSelectActor`) abre um popup (`arenaActionPanelHTML`, `.arena-action-overlay`/`.arena-action-overlay-card`) com um menu de quatro opções: **Atacar**, **Usar Item**, **Trocar de Pokémon**, **Fugir** (`SESSION.arenaAction`). Antes era um `.card` fixo no fluxo normal da página (precisava rolar até ele, e de novo até o alvo/tile de troca lá em cima); agora é um popup centralizado, maior, que de cara já mostra quem está em campo, **lado a lado, um bloco por Time** (`arenaActionBattlefieldHTML`, `.arena-action-battlefield`/`.arena-action-team-col` — um `<div>` por `STATE.arena.teams`, cada um listando as próprias entries via `arenaEntryHTML` de novo, o mesmo card que já existe no campo de batalha, então a lógica de clique/elegibilidade E o gatilho **"📊"** de abrir o painel de Atributos não são duplicados em lugar nenhum). Quando um Movimento/Item pede um alvo manual, é a própria `arenaEntryHTML` de cada entry (já calculada como `arena-slot-targetable`, via a mesma checagem `pickingTarget`/`eligibleMoveTargets`/`eligibleItemTargets` que o campo de batalha normal usa) que fica clicável ali dentro do popup — sem uma "grade de alvos" separada, é literalmente clicar em quem já está no campo mostrado. Trocar reaproveita `arenaSourceTilesRowHTML(t)` (fatorada de `arenaTrainerSourceHTML`, que agora só chama essa função pros próprios tiles) num bloco à parte pra quem NÃO está em campo (Equipe ativa). Se o Pokémon estiver Confuso, o teste da Confusão (ver abaixo) roda automaticamente antes desse popup abrir. Escolhendo Atacar, aí sim se escolhe o Movimento; o alvo (se precisar de um) vem depois. O motor resolve a Precisão (Cap. 10, com fallback automático pra sempre-acerta em Movimentos sem Precisão definida — inclusive corrigindo fichas salvas de antes dessa checagem existir, via `migratePokemonMoves`), Crítico (Cap. 11), Dano (Cap. 12) e Tipos (Cap. 13) com 1d6, e o Efeito Percentual (Cap. 14) com 1d10 quando o Movimento tiver um efeito de status conhecido — se aplicar, a Condição já entra sozinha na ficha do alvo, respeitando a regra de nunca empilhar duas Condições Principais (Confusão é a exceção, Cap. 20). PV chegando a 0 marca Desmaio (Cap. 19) automaticamente. **Card da Arena mais respirado**: `.arena-slot` ganhou mais largura/espaçamento (78px→84px, gap 12px→16px entre cards) — o aviso **"😵 Escolher próximo"** (Cap. 25/59, texto comprido) saiu de `.arena-turn-badge` (`position:absolute`, pensado pro rótulo curto "▶ Turno" — flutuando por cima acabava cobrindo o PV e a sprite por baixo, reportado com print) e ganhou a própria classe `.arena-fainted-banner`, no fluxo normal do card (não flutua, empurra o resto pra baixo em vez de sobrepor).
- **Popup de Ação fecha assim que a escolha é enviada (Cap. 79, revisado pelo Cap. 86)**: `arenaQueueAction` chama `arenaResetActionState()` logo depois de gravar o *bundle* em `round.actions` — quem escolheu não fica mais olhando um popup congelado esperando o resto da mesa escolher, e depois ainda o Mestre resolvendo a Rodada clique a clique (Cap. 86); o popup e o quadro de dado JÁ NÃO precisam mais dividir a mesma janela, porque escolher deixou de ser o mesmo instante que resolver. ## Área PVP (combates rápidos, sem Mestre)

Botão **"⚔️ PVP"** no topo — um modo à parte da Arena do RPG, pedido do usuário pra "combates rápidos" que "não dependa de mestre" e cujas regras de Pokémon/combate "vão ser atualizadas lá simultaneamente toda vez que eu fizer uma alteração no RPG, de tudo". Ainda exige login com uma conta de Treinador cadastrada (mesmo PIN de sempre) — só a partir daí é 100% self-service.

- **O motor de combate NÃO é copiado — é o mesmo código da Arena, chamado de verdade.** `withArenaContext(arenaObj, fn)` aponta `STATE.arena` temporariamente pra dentro de uma sala de PVP, chama `fn()` síncrono (o site inteiro roda em JS de thread única, sem `await` no meio de uma ação) e devolve o ponteiro pro normal no `finally` — o suficiente pra reaproveitar sem mudar uma linha `arenaLog`, `arenaQueueAction`, `arenaResolveNextStep`, `arenaComputeResolveOrder`, `arenaCheckVictory`, `applyEndOfTurnStatusAndLog`, `arenaStatusActionPreCheck`/`arenaConfusionPreCheck`, `eligibleMoveTargets`, `computeInitiativeOrder`, `arenaBuildSelectingRound`, `DT.resolveArenaMove` e `DT.arenaSwapInResolved` — o Cap. 86 inteiro (seleção simultânea, ordem por Prioridade/Iniciativa, Paralisia/Sono/Congelamento/Confusão, Habilidades, PP, Estágios) roda idêntico dentro de uma sala. Qualquer ajuste futuro nessas funções (uma correção de regra, um novo gatilho de Habilidade) já vale pra PVP também, sem precisar lembrar de mexer em dois lugares — não existem duas cópias do motor.
- `findTrainer(id)` ganhou um fallback: além de `STATE.trainers` (Treinadores de verdade), reconhece um "treinador virtual" em `STATE.arena.virtuais[id]` quando existir — só populado enquanto `STATE.arena` estiver apontando pra uma sala via `withArenaContext`. Pro motor de combate, um treinador virtual de PVP é só mais um Treinador qualquer; fora de qualquer sala (`STATE.arena` de volta à Arena normal do RPG), esse fallback nunca é alcançado — zero risco pro código existente.
- **Bug real achado pelo usuário ("a Arena tá impactando o PVP")**: `withArenaContext` troca `STATE.arena` só durante a chamada SÍNCRONA de `fn()` — mas o quadro de dado da Arena (`#diceOverlay`) anima em `setInterval`, ASSÍNCRONO. Como nenhum timer dispara no meio de uma chamada síncrona, o 1º frame do quadro de dado (dentro do próprio `withArenaContext`) mostrava a sala certa, mas todo tick seguinte (90ms depois, já fora do `withArenaContext`, com `STATE.arena` de volta ao normal) relia `STATE.arena.lastRoll` — a Arena de VERDADE, não a sala — mostrando dado errado (ou nada) pro resto da animação, TODA VEZ que alguém agia na Área PVP. Corrigido com `ARENA_CONTEXT_DEPTH` (contador incrementado/decrementado por `withArenaContext`): `checkArenaRoll()` e `renderDiceOverlay()` agora saem cedo enquanto ele for >0 — a Área PVP nunca precisou desse quadro mesmo (a Rodada resolve tudo de uma vez, sem pausa nenhuma pra ver o dado rolando), então bloquear ali não tira nada dela, só corta o vazamento pra Arena de verdade. Mesma trava em `arenaResetActionState()` — sem ela, um caminho raro dentro de `DT.resolveArenaMove` (Movimento sem alvo válido na hora de resolver) zerava o popup de Ação da Arena de VERDADE se a mesma pessoa tivesse um aberto (mesma sessão/aba, outro momento) bem na hora de uma Rodada de PVP resolver. Testado (`test_pvp.js`): confirmado que o bug realmente acontecia sem a trava (regressão provada desativando-a manualmente) e que os dois caminhos ficam mudos/intactos com ela.
- **Modelo de dados**: `STATE.pvp = { fichas: {[trainerId]: [...] }, salas: {[salaId]: {...}} }`, dentro do mesmo `STATE` sincronizado de sempre (sem storage novo). `fichas[trainerId]` é o "box" de Pokémon de PVP daquele Treinador — **independente** do Time do RPG (`t.pokemons`/`t.banco`), criado/editado/removido pelo próprio jogador (`DT.pvpAddFicha`/`pvpRemoveFicha`/`pvpSetFichaField`/`pvpSetNatureza`/`pvpSetHabilidade`/`pvpSetMoveField`), sem Mestre nenhum por trás. Cada `sala` guarda **exatamente a mesma forma** que `STATE.arena` (`teams`, `entries`, `round`, `log`, `vencedor`, `fugaTravada`) mais `jogadores` (lobby) e `virtuais` (um treinador virtual por jogador, só dessa sala) — é o que permite apontar `STATE.arena` pra ela via `withArenaContext` sem tradução nenhuma.
- **Nível fixo, Atributos sempre no máximo** (resposta do usuário às perguntas de escopo): toda ficha de PVP nasce com `vinculo=25` travado (nunca editável — nem existe o campo na tela) e, ao entrar numa sala, ganha um treinador virtual com os 6 `attrPoints` em 5/5 (`pvpMaxTrainer()`/`sala.virtuais[vid]`) — como `hpMax`/`effectiveStat` já são funções puras de `(trainer, poke, stat)`, isso já entrega o Atributo Efetivo máximo sem mexer nas fórmulas. O jogador só escolhe **Espécie, Movimentos, Natureza e Habilidade** (mesmos `applySpeciesData`/`findNatureByName`/`habilidadesSelecionaveisDaEspecie` da ficha do RPG — mesma base oficial da PokeAPI, então atualização de dado de espécie também já vale pro PVP automaticamente).
- **"Nível 16" de verdade, não só um número solto** (correção do usuário — "os pokémon do PVP tem que estar todos no nível máximo do RPG, ou seja 16"): `var PVP_LEVEL = 16` é literalmente o próprio teto de Nível de Treinador do sistema (`attrBudget`/`officialLevelCeiling` já travam em `clampInt(nivel,1,16)` — 16 não é um valor inventado pro PVP, é o mesmo 16 que qualquer ficha do RPG esbarra ao chegar no topo). Usado só pra alimentar `officialLevelCeiling(PVP_LEVEL)`, o teto de Nível oficial que filtra o Learnset de Movimentos aprendidos por Nível.
- **Movimentos restritos ao Learnset real da Espécie — nunca mais um nome digitado à mão**: o builder de ficha (`pvpFichaCardHTML`) trocou o campo de texto livre (que deixava, por exemplo, um Charizard ganhar Hydro Pump) pelo **mesmo seletor "Learnset" do Treinador no RPG** (`movePickOptions(LEARNSETS[especieNum], metodo, officialLevelCeiling(PVP_LEVEL))`, botões Nível/Evo/TM/Egg) — o jogador só escolhe entre as opções que a própria PokeAPI (via `LEARNSETS`) diz que aquela Espécie aprende de verdade, no método escolhido. `DT.pvpSetMoveMethod(pid,idx,metodo)` troca o método (limpando o slot — o Movimento anterior pode não existir no novo método); `DT.pvpSetMoveSelect(pid,idx,el)` valida de novo no servidor (função) que o nome escolhido está de fato em `movePickOptions` daquele método/teto antes de aplicar — nunca aceita um Movimento fora da lista, mesmo chamado direto (defesa em profundidade, igual ao resto do motor).
- **Times completos, até 6, com troca** (resposta do usuário): cada sala tem exatamente 2 jogadores (Time A/B); no lobby de cada sala (`pvpTeamPickHTML`), cada um escolhe até 6 fichas do próprio box (`DT.pvpToggleFichaNoTime`) e clica **"✓ Pronto"** (`DT.pvpFicarPronto`) — assim que os DOIS estiverem prontos, `pvpTryStartBattle` monta os treinadores virtuais (cada um recebendo as fichas escolhidas como `pokemons`, igual a Equipe ativa do RPG) e a Rodada 1 já começa sozinha, sem ninguém clicar "Iniciar Batalha". Trocar durante a batalha reaproveita o mesmo caminho do RPG (`DT.pvpTrocarEscolher`→`arenaQueueAction{kind:'trocar'}`, `DT.pvpTrocarForcado`→`DT.arenaSwapInResolved` pra quem desmaiou ou tem um convite de troca livre pendente tipo U-turn).
- **Turno passa sozinho assim que os dois agem — sem Mestre nenhum controlando** (resposta do usuário): `arenaQueueAction` (reaproveitada sem mudança) já vira a Rodada de `'selecting'` pra `'resolving'` sozinha assim que todo mundo elegível escolheu — isso nunca dependeu do Mestre, nem no RPG. O que o RPG tornou manual foi só o AVANÇO passo a passo depois disso (Mestre clicando "▶️ Avançar", ver a seção da Arena acima); pra PVP, `pvpDriveResolution(sala)` chama `arenaResolveNextStep` num laço até a Rodada sair de `'resolving'` (terminou e já abriu a seleção da próxima sozinha, ou a batalha acabou) — a Rodada inteira resolve de uma vez, sem clique nenhum de ninguém no meio.
- **Várias salas em paralelo** (resposta do usuário): cada sala tem o próprio `entries`/`round`/`log`/`virtuais` isolado — duas batalhas simultâneas nunca se enxergam. O id do treinador virtual é `pvp_<trainerId>_<salaId>` (prefixo `pvp_` nunca bate com um id real de `STATE.trainers`, sufixo por sala evita colisão entre salas do mesmo Treinador). As fichas em si **não são clonadas** — `sala.virtuais[vid].pokemons` guarda referência direta pra `STATE.pvp.fichas[trainerId]` (dano/status/PP mexem na ficha de verdade), então uma ficha ganha `emBatalha=salaId` ao entrar numa sala e fica bloqueada pra qualquer outra sala em paralelo até essa batalha terminar.
- **Cura automática ao fim + Desistir** (pedidos do usuário): `pvpFinishBattle(sala)` roda sempre que `sala.vencedor` é decidido (vitória por PV zerado, igual ao RPG, OU por Desistir) — `pvpHealAll` zera PV/Condição/Confusão/PP/Estágios de toda ficha envolvida (`resetStages` reaproveitado) e libera `emBatalha=null`. Sala esvaziada (todo mundo saiu) é removida de `STATE.pvp.salas` — sem lixo acumulando com o tempo.
  - **Bug real achado pelo usuário ("alguns pokémon estão ficando presos em batalhas... mesmo depois de sair")**: o comentário original de `pvpHealAll` dizia que `sala.virtuais[...].pokemons` era uma referência direta pra ficha de verdade em `STATE.pvp.fichas[trainerId]` — e É, mas só até o 1º round-trip pelo Firestore (`queueSave`, debounced 400ms). `onSnapshot` faz `STATE = doc.data()`, um deserialize do zero sem noção nenhuma de referência compartilhada — passados uns 400ms do início da batalha (qualquer batalha real dura vários turnos), `sala.virtuais[vid].pokemons[i]` e `STATE.pvp.fichas[trainerId][j]` viram DUAS CÓPIAS independentes da mesma ficha original. Curar/destravar só a cópia de dentro da sala nunca chegava na ficha de verdade — ela ficava com `emBatalha=<sala já apagada>` PRA SEMPRE. Testado simulando o round-trip de verdade (fichas viram cópias via `JSON.parse(JSON.stringify(...))` no meio de uma batalha) e confirmando que a regressão realmente acontecia sem o fix.

Cobre qualquer ficha que já tenha ficado presa antes desse fix (ou qualquer outro jeito ainda não previsto de uma trava sobrar) — só o dono da própria ficha pode liberar a própria.
- **Bug real achado pelo usuário ("quando eu atualizo a página ele volta a vida dos pokémon como se eu tivesse reiniciado", "não tá dando pra continuar o combate")**: o SDK de verdade do Firestore **rejeita `.set()` inteiro** (a Promise cai em `.catch`, nada é salvo) se **qualquer** valor em **qualquer** lugar da árvore do documento for `undefined` (não é `null` — é `undefined` mesmo). `resolveAttack` monta um `result` que vira `STATE.arena.lastRoll.alvos[i]` (ou `sala.lastRoll` dentro de uma sala de PVP, via `withArenaContext`) — e `result.typeMod` ficava `undefined` em dois caminhos: (a) todo Movimento de Status (`isDamaging ? tm.mod : undefined`, de propósito, pra nunca aparecer "Super/Pouco Efetivo" numa Status) e (b) qualquer Ataque que ERRASSE o alvo (`if(!hit){ result.dano=0; return result; }` retorna ANTES da linha que define `typeMod`, deixando a chave nem existir). Como o fake Firestore do harness de teste sempre resolve `.set()` com sucesso (não replica essa validação de verdade), esse bug nunca foi pego pela suíte — só apareceu jogando de verdade. Efeito prático: bastava um golpe de Status OU um erro de mira em qualquer batalha (Arena ou PVP) pra `doSave()` seguinte falhar **em silêncio** — o site continuava parecendo funcionar normalmente na tela (o `STATE` em memória seguia mudando), mas nada mais daquele ponto em diante estava realmente chegando no banco; um F5 puxava de volta o último save que TINHA funcionado, "voltando no tempo" a batalha inteira (às vezes até quase o começo). Dois fixes, um específico e um geral: `resolveAttack` agora seta `result.typeMod = null` nos dois caminhos (Status e erro de mira) em vez de deixar `undefined`; e `doSave()` ganhou `sanitizeForFirestore(state)` — um round-trip por `JSON.parse(JSON.stringify(...))` (que já remove toda chave com valor `undefined`, comportamento nativo do `JSON.stringify`) aplicado a `STATE` **antes** de todo `.set()` de verdade (inclusive o de primeira inicialização do banco) — uma rede de segurança geral contra essa classe inteira de bug, não só contra esses dois caminhos já achados, caso outro apareça no futuro num motor de combate deste tamanho. Testado com um script de reprodução dedicado (simulando o `.set()` de verdade rejeitando `undefined`, coisa que o harness de teste normal não fazia) confirmando o bug acontecendo sem o fix e sumindo com ele; `test_battle.js` ganhou testes permanentes pros dois caminhos (`typeMod===null` numa Status e num Ataque que erra) e um teste direto de `sanitizeForFirestore` (remove `undefined` aninhado em objeto/array, preserva `null` e o resto dos dados).
- **Escolher o líder antes de começar** (pedido do usuário: "Deixe escolher, qual dos pokémon escolhidos queremos mandar pro combate antes de começar direto. Você tá pegando o primeiro dos 6 e iniciando"): `pvpTryStartBattle` usava sempre `fichas[0].id` (o 1º da lista, só por acaso da ordem de clique) como quem entra em campo — agora cada `jogador` ganha um campo `lider` (id de ficha), escolhido via `DT.pvpEscolherLider(salaId, pid)` DEPOIS de montar o time (`pvpTeamPickHTML` mostra "Quem vai pro campo primeiro?" assim que o 1º Pokémon é escolhido, que já nasce marcado como líder padrão — o jogador troca se quiser). `DT.pvpFicarPronto` agora recusa ficar pronto sem um `lider` válido (ainda dentro do time escolhido); `DT.pvpToggleFichaNoTime` limpa `jogador.lider` se a ficha removida do time era a marcada. Igual ao resto da montagem de time, o adversário só vê "pronto" — nunca QUEM foi escolhido como líder — até `pvpTryStartBattle` rodar de verdade e revelar os dois de uma vez (mesma "revelação simultânea" já usada pras ações de Ataque, Cap. 86). Testado (`test_pvp.js`): fluxo completo com os DOIS jogadores escolhendo o 2º Pokémon do time (não o 1º) como líder, confirmando `entries[].pokemonId` bate com o líder escolhido — regressão provada revertendo o fix e confirmando que voltava a pegar `fichas[0]`.
- **Dado 3D + resolução com pausa dramática** (pedido do usuário: "Após os ataques a resolução tá sendo muito rápida. Espere uns segundos... você consegue configurar um [dado] 3D? Como se ele tivesse caindo numa mesa e rolando?"): a resolução de verdade (`pvpDriveResolution`) continua 100% síncrona e instantânea de propósito — atrasá-la criaria risco de corrida entre os dois clientes decidindo quem resolve o quê. Em vez disso, toda rolagem real que acontece durante o laço (`sala.lastRoll` mudou) é copiada pra `sala.rollQueue` (persistida, capada em 12 entradas) via `pvpQueueRoll` — o "espere uns segundos" e o quadro de dado são encenação 100% cosmética, client-side, tocada a partir dessa fila (`pvpCheckRoll`, chamada a cada `render()`, encontra rolagens novas por `ts` contra uma marca-d'água local `PVP_DICE_SEEN_TS[salaId]` — a 1ª vez que uma sala aparece numa aba, a marca nasce no fim da fila, sem reprisar rolagens antigas depois de um F5 no meio da batalha). `pvpAdvanceDiceQueue`/`pvpScheduleDiceStage` tocam uma rolagem de cada vez (`PVP_DICE_ANIM`), com `setTimeout` reais (nunca bloqueiam nada — o tabuleiro já está certo há tempos, só a REVELAÇÃO na tela é que espera). **100% independente do `#diceOverlay` da Arena** (`#pvpDiceOverlay`, `pvpRenderDiceOverlay`, `pvpDiceOverlayHTML` — nem globals, nem CSS, nem função em comum além de utilitários puros como `rollSummaryLines`/`diceStagesFor`, que só recebem o objeto da rolagem por parâmetro; nunca lê/escreve `STATE.arena`) — mesmo espírito de sempre ("Eles tem que ficar totalmente independentes"), e por isso nem precisa do `ARENA_CONTEXT_DEPTH`. ## Rotas por link (#pvp / #arena / #ficha)

Pedido do usuário: "as páginas estão agrupadas todas... é possível o PVP ter um link, a Arena ter outro e a ficha ter outro? Em todos eles a regra acompanha, abrindo como se fosse popup." Continua sendo um arquivo HTML só (GitHub Pages puro, sem servidor/roteador nenhum) — a "separação" é por `#hash` na URL, sincronizado com o estado da SPA:

- `currentRouteHash()` decide o hash certo pra cada combinação de `SESSION.showArena`/`showPvp`/`screen` (MESMA ordem de prioridade de `screenHTML()` — Arena antes de PVP — pra nunca mentir sobre qual tela está de fato visível). `syncRouteHash()`, chamada no fim de todo `render()`, escreve esse hash na barra de endereço via `history.replaceState` (nunca `location.hash=`) — de propósito: `replaceState` NUNCA dispara o evento `hashchange` sozinho (só navegação de verdade dispara), então sincronizar a cada `render()` enquanto TAMBÉM se escuta `hashchange` não cria loop nenhum, sem precisar de nenhuma trava manual contra reentrância.
- `applyRouteFromHash()` faz o caminho inverso: lê `#pvp`/`#arena`/`#ficha` e ajusta `SESSION` — chamada uma vez no boot (link direto/recarregar a página no meio de uma das 3 telas já abre nela) e de novo a cada `window.addEventListener('hashchange', ...)` (colar um link novo na barra, ou Voltar/Avançar do navegador).
- `DT.toggleArena`/`DT.togglePvp` agora se excluem sozinhos ao abrir (abrir a Arena fecha o PVP e vice-versa) — antes dava pra empilhar os dois (SESSION.showArena e showPvp ambos true), o que nunca quebrava a tela (screenHTML() já tinha uma ordem de prioridade), mas não fazia sentido pro modelo de "3 páginas próprias" que esse pedido pede.
- **Regras continua sendo só um popup por cima de qualquer uma das 3 (de propósito, sem hash próprio)**: `currentRouteHash()` nem olha pra `SESSION.showRules` — abrir/fechar Regras nunca mexe no link da tela de baixo, exatamente como pedido ("a regra acompanha, abrindo como se fosse popup").
- Não vira 3 arquivos/páginas de verdade nem precisa de servidor: `file://`/GitHub Pages já entendem `#hash` nativamente, incluindo compartilhar o link (`.../diario-de-treinador.html#pvp`) — ainda passa pelo login normal (PIN) de qualquer jeito, o link só pula direto pra tela certa depois de entrar.
- Testado (`test_render.js`, com `location`/`history`/`addEventListener` de mentirinha no harness): estar em cada tela mantém o hash certo, abrir uma fecha a outra (Arena↔PVP), abrir/fechar Regras não muda o hash, `#ficha` funciona, e disparar `hashchange` na mão (simulando colar um link ou usar Voltar/Avançar) abre a tela certa. 3 regressões provadas (sync desligado, exclusão mútua desligada).

## Leva de correções de mecânica (Substitute, Leech Seed, Flinch, Stealth Rock, Healing Wish, Outrage, Foul Play, popup de Regras, abas independentes, gerador aleatório de PVP...)

Pedido do usuário, de uma vez só, começando por uma instrução geral: "Antes de começar, peço que tudo que tu revisar e corrigir, faça uma varredura e veja se existem coisas que tenham a mecânica parecida para que você possa acertar e já vai corrigindo" — com **pokemondb.net** (referência rápida) e **bulbapedia.bulbagarden.net** (referência elaborada) como fonte pra conferir cada mecânica oficial antes de converter pro sistema. Todo item abaixo foi corrigido no motor **compartilhado** (`resolveAttack`/`applyAttackResult`/`resolveMoveUse`/`DT.resolveArenaMove`/`arenaExecuteQueuedAttack`/`DT.arenaSwapInResolved`), então vale pra **Arena e PVP ao mesmo tempo**, sem código duplicado (mesmo princípio do `withArenaContext` da seção acima) — testado com `test_battle.js` (regra em si) e a suíte completa (`test_pvp.js`/`test_render.js`/`sweep_moves.js`) rodada de novo a cada mudança pra caçar regressão, sempre com o ciclo de "desativar o fix na mão, confirmar que o teste quebra do jeito esperado, restaurar" antes de qualquer coisa ser considerada pronta.

- **Substitute** (pedido do usuário: "Revise o funcionamento do Substitute, o usuário deveria perder vida para colocar o boneco e ele tem a vida dele própria baseada na vida do usuário"): antes era só texto de dex, sem efeito nenhum. Agora é um golpe especial (mesmo padrão de "não passa pelo pipeline normal de dano/Precisão" dos Movimentos de carga) — custa exatamente 25% do PV Máximo (arredondado pra baixo), falha se o usuário não tiver MAIS que isso de PV atual (nunca desmaia usando Substitute) e falha também se já tiver um Substituto de pé (só um por vez); o boneco nasce com PV igual ao gasto e absorve dano de golpes recebidos (sem vazar excesso pro PV de verdade quando quebra) e bloqueia por completo qualquer Movimento de Status/efeito colateral enquanto estiver de pé. `resetStages` (saída de campo) derruba o boneco junto, igual às outras condições voláteis novas.
- **Leech Seed** (pedido do usuário, convertendo a descrição oficial do Bulbapedia pro sistema): drena 1/8 do PV MÁXIMO do semeado no fim de cada turno dele, restaurando pro semeador **ou quem tomar o lugar dele** (resolvido de novo por `trainerId` a cada tique — nunca um `pokemonId` fixo, então troca de campo já cobre sozinha). Não pega em Pokémon do Tipo Grama (imune). Funciona tecnicamente contra Magic Guard (planta a semente), mas nenhum PV é drenado. Segurando Big Root aumentaria a cura em 30% (item ainda não simulado neste sistema — fica de fora por enquanto, igual outros itens segurados). Contra Liquid Ooze, o SEMEADOR perde a mesma quantidade que ia ganhar, em vez de curar. Limpa ao trocar de campo (`resetStages`) ou usando Rapid Spin (novo gancho em `DT.resolveArenaMove`, só quando o golpe acerta de verdade).
- **Flinch/Atordoado** (pedido do usuário: "flinched é uma mecânica que tem que ser aplicada no game. Só que só pode ser aplicada no turno em que ela for ativada... se eu for o último a atacar e aplicar flinched, ele não vai pro próximo turno com a condição"): mecânica inteira nova (não existia nenhuma versão anterior, nem quebrada). `MOVE_FLINCH` cataloga os ~34 Movimentos reais com chance de causar Flinch (conferidos um a um contra pokemondb/Bulbapedia — Low Kick foi cogitado e DESCARTADO depois de confirmar que a chance de Flinch dele só existiu nas Gerações 1-2, removida das gerações atuais) rolando o mesmo d10 de Efeito Percentual (ver o item "condição pura" abaixo). A flag (`poke.flinched`) é checada e CONSUMIDA na hora exata da própria vez do atordoado chegar dentro da MESMA Rodada — nunca sobra pra Rodada seguinte, mesmo se quem causou o Flinch foi o ÚLTIMO a agir (limpeza geral em `arenaFinishRoundResolution`/`clearAllFlinch` cobre esse caso). Inner Focus bloqueia de vez, nunca chega a marcar a flag.
- **Stealth Rock** (pedido do usuário: "Ele precisa funcionar afetando o campo do adversário que eu mirar"): a causa raiz era a categoria de alvo — `'field'` não pede alvo nenhum (`eligibleMoveTargets` devolve `[]` pra essa categoria), então o golpe nunca sabia QUAL time afetar e só logava "ainda não simulado". Virou categoria `'foe'` (reaproveita o MESMO seletor de alvo único que Thunder Wave/Toxic já usam — "mirar" um inimigo, literalmente) e o motor aplica a armadilha no TIME (`STATE.arena.hazards[teamId].stealthRock`) desse alvo escolhido, não só nele. O dano de entrada (`applyStealthRockOnSwitchIn`, chamado de `DT.arenaSwapInResolved` — único lugar onde um Pokémon novo pisa em campo, cobrindo troca normal, forçada por desmaio e U-turn/Volt Switch/Parting Shot) segue a tabela oficial de Efetividade de Tipo Pedra: 4×→metade do PV Máximo, 2×→1/4, 1×→1/8 (padrão), 1/2×→1/16, 1/4×→1/32 — Pedra não tem imunidade de Tipo nenhuma, então sempre cai numa dessas 5 faixas. Spikes/Toxic Spikes/Sticky Web continuam de fora por enquanto (mesmo formato de golpe, mas não foram pedidos nesta leva).
- **Healing Wish / Lunar Dance** (pedido do usuário: "Healing wish também não está funcionando... O usuário vai a 0 de hp e cura o aliado que entrar em campo tanto com vida e condições"): também um golpe especial auto-alvo — o usuário desmaia NA HORA (`currentHP=0`) e a cura de verdade só acontece quando outro Pokémon do MESMO Treinador entrar em campo (`trainer.healingWishPending`, consumido em `DT.arenaSwapInResolved`, mesmo espírito "por trainerId" da Leech Seed) — PV cheio e a Condição Principal curada (Queimadura/Veneno/Paralisia/Sono/Congelamento; Confusão fica de fora de propósito — é uma condição à parte que Healing Wish nunca curou em nenhuma geração oficial). Lunar Dance é o mesmo golpe, só que também restaura o PP de todos os Movimentos até o máximo.
- **Outrage/Thrash/Petal Dance** (pedido do usuário, convertendo a descrição oficial: "attacks for 2-3 turns, during which it cannot switch out, and then becomes confused... If Outrage is disrupted... it will stop and not cause confusion. Pokémon with the ability Own Tempo or those behind a Substitute cannot be confused"): ao contrário dos Movimentos de carga, este golpe ATACA todo turno, normal — só a REPETIÇÃO automática (sem passar pelo menu, o que também cumpre sozinho o "cannot switch out") e a duração (2 ou 3 turnos, sorteada no 1º acerto) são novas (`poke.outrageLock`). Ao completar a duração inteira sem interrupção, o usuário fica Confuso de exaustão (bloqueado por Own Tempo ou Substituto de pé, igual pedido) — reaproveitando o sistema de Confusão JÁ existente, sem duplicar a própria mecânica de auto-dano dela. Perturbação (errar o golpe, ou não conseguir agir por Paralisia/Sono/Congelamento/Flinch/Confusão) encerra a fúria sem Confundir — EXCETO se a perturbação acontecer bem na última rodada da fúria, que ainda assim confunde (fonte: Bulbapedia — "If a disruption occurs on what would have been the final, confusion-inducing turn of Thrash, the user will still become confused").
- **Foul Play** (pedido do usuário, convertendo a descrição oficial: "Foul Play uses the opponent's Attack stat instead of the user's in damage calculation"): antes era um golpe físico comum, usando o próprio Ataque do usuário. Agora `resolveAttack` detecta esse golpe pelo nome e usa o Ataque Efetivo do DEFENSOR na fórmula de dano (com a interação de Unaware preservada, só invertendo de qual lado ela olha) — testado comparando lado a lado com um Tackle de mesmo Poder num cenário onde o defensor tem Ataque bem mais alto que o atacante.
- **Golpes de condição pura, d6 → d10** (pedido do usuário: "Vamos trocar a rolagem dos moves que são só pra causar alguma condição para D10 em vez de d6. ## Quadro de dado restrito à tela certa e a quem participa

Pedido do usuário: "O dado tá rolando no site todo. Tem que rolar só na tela da arena quando a luta for lá e só na tela do pvp quando a luta for lá. Para não atrapalhar a navegação dos demais jogadores no restante do site. E o ideal é rodar só pra quem tá participando do combate e do mestre."

Bug real de arquitetura: tanto `#diceOverlay` (Arena) quanto `#pvpDiceOverlay` (PVP) são `<div>`s **irmãs** de `#app`, fora do HTML trocado por `screenHTML()` — sempre presentes na página não importa a tela. `SESSION.showRollOverlay`/`SESSION.showPvpRollOverlay` nunca checavam `SESSION.showArena`/`SESSION.showPvp` nem quem estava vendo, só se havia uma rolagem nova em `STATE.arena.lastRoll`/`sala.rollQueue` — e como esses dados são sincronizados via Firestore pra TODO MUNDO conectado, qualquer rolagem de qualquer batalha aparecia por cima de qualquer tela (Ficha, Regras, Início...) de qualquer pessoa conectada, participando ou não.

- **Correção ficou isolada na hora de DESENHAR, nunca no cronômetro interno**: a 1ª tentativa gateou `checkArenaRoll()`/`pvpCheckRoll()` inteiros (as funções que decidem se uma rolagem nova começa a animar) — e isso quebrou o próprio fluxo de resolução: o timer da animação (`startDiceRollAnimation`) é o mesmo que libera de novo o popup de Ação de quem ACABOU de agir (`SESSION.arenaResolving`, via `arenaFinishRoll`/`arenaResetActionState`) — travando pra sempre quem resolveu a própria ação sem `SESSION.showArena` setado exatamente como a checagem exigia (achado rodando a suíte de testes: quebrava o fluxo de Ação inteiro). A correção final ficou só na função que produz o HTML (`diceOverlayHTML`/`pvpDiceOverlayHTML`) — `arenaDiceViewerAllowed()` decide se ESSA sessão, nesse instante, tem o direito de ver o quadro: `SESSION.showArena` true, e (Mestre OU tem pelo menos um Pokémon de verdade em `STATE.arena.entries` — nunca um jogador só de passagem/espectador); pro PVP, `SESSION.showPvp` true (`pvpSalaDoJogador` já restringia por quem participa, só faltava a tela). O cronômetro/estado interno (`checkArenaRoll`, `PVP_DICE_ANIM`, etc.) continuam rodando exatamente como antes pra qualquer sessão — só o que aparece na tela (o `<div>`) é que passou a checar quem está olhando; deixar um timer correndo à toa numa aba que nunca vai mostrar nada é inofensivo.
- Cobre também "navegou pra outra tela NO MEIO da rolagem": como a checagem roda a cada frame de desenho (não só na largada), sair da Arena/PVP enquanto o dado ainda está girando esconde o quadro na hora, sem esperar a animação terminar — e voltar pra tela certa mostra a animação em qualquer estágio em que ela estiver naquele momento.
- Testado (`test_battle.js`/`test_pvp.js`): participante de verdade na tela certa vê o quadro; jogador só navegando (sem Pokémon na batalha), mesmo na tela certa, não vê; participante fora da tela não vê; Mestre sempre vê enquanto estiver na tela da Arena (participante ou não), mas não fora dela; saindo da tela do PVP no meio de uma rolagem o quadro some na hora e volta ao reentrar. 2 regressões provadas (Arena e PVP) desativando cada checagem e confirmando as falhas esperadas.

## Popup de Ação e overlays de dado não reanimam a cada re-render (fim do "piscar")

Pedido do usuário: "Quando eu clico pra ação de um pokémon ele abre o popup, tá certo. Mas toda vez que eu clico, dentro do popup dele, pra fazer outra coisa, ele fecha o popup rápido e abre outro com a opção que pedi. Não tem como isso ser tudo feito dentro de um popup só não? Fica muito esquisito. E o dado também tá nessa, cada animação de rolagem dele ele fica abrindo e fechando o popup dele rapidão até dar o resultado. Queria algo contínuo que simularia aí uma suavidade."

Bug real de arquitetura, não de fluxo: o popup de Ação (`arenaActionPanelHTML`) e os dois overlays de dado (`diceOverlayHTML`/Arena, `pvpDiceOverlayHTML`/PVP) já eram tecnicamente "um popup só" — a mesma `<div>` cobre menu → escolher Movimento/Item → escolher alvo → Resolvendo, e o mesmo overlay cobre d6 → 1d10 → resultado assentado, tudo via a MESMA identidade (`SESSION.arenaAttacker`, `STATE.arena.lastRoll.ts`) sem nenhum popup fechando de vez e outro abrindo no meio do caminho. O problema é que `render()` reconstrói o HTML **inteiro** do zero a cada clique/tick de animação (`document.getElementById('app').innerHTML = screenHTML()`, e o mesmo padrão nos dois `<div>` irmãs `#diceOverlay`/`#pvpDiceOverlay`) — o navegador vê um elemento `<div class="...">` **novo** a cada render e replaya a animação CSS de entrada (`dice-fade-in`/`dice-pop-in`) toda vez, dando a impressão de "fechou e abriu rapidinho", mais visível ainda no overlay de dado porque ele reanima a cada ~90ms (o tick da rolagem) até assentar.

- **Correção**: rastrear a identidade real de cada popup/overlay num var de módulo (`ARENA_ACTION_POPUP_OPEN_FOR` = `SESSION.arenaAttacker`; `DICE_OVERLAY_OPEN_FOR` = `STATE.arena.lastRoll.ts`; `PVP_DICE_OVERLAY_OPEN_FOR` = `roll.ts` do PVP) e comparar contra o valor da vez anterior: só quando a identidade muda (abertura nova de verdade, ou uma rolagem realmente nova) a função de desenho omite uma classe extra (`-noanim`); enquanto a MESMA identidade continuar aberta/rolando, a classe é acrescentada — e regras CSS de seletor composto (`.dice-overlay.dice-overlay-noanim{ animation:none; }` etc., 6 regras ao todo, 2 por superfície) fazem essa classe desligar a animação. Cada função zera seu rastreador pra `null` assim que o popup/overlay fecha de vez (`SESSION.arenaAttacker` nulo, `SESSION.showRollOverlay`/`showPvpRollOverlay` falso) — garantindo que a PRÓXIMA abertura sempre anima normal, e a identidade nunca fica "presa" sem animação pra sempre.
- Mesma técnica já existia isolada pro caso `arenaResolving` (`.arena-action-overlay-resolving{ animation:none; }`, evitando o quadro de dado por cima duplicar o fundo escuro) — generalizada aqui pras 3 superfícies inteiras.
- Testado (`test_render.js`, seção "Cap. 120"): popup de Ação anima na 1ª abertura, não reanima ao re-renderizar a mesma entrada nem ao trocar de passo dentro dele (menu → Movimento), volta a animar só numa abertura nova de verdade (depois de Cancelar); overlay de dado da Arena e do PVP, testados direto nas funções de desenho — 1º frame de uma rolagem anima, ticks seguintes da mesma rolagem (mesmo `.ts`) não reanimam, quadro final assentado continua sem reanimar, uma rolagem nova de verdade volta a animar. Regressão provada: revertendo o cálculo da classe (`noAnimClass` sempre `''`) o teste de "re-render da mesma entrada não reanima" falha exatamente como esperado; restaurado, a suíte completa passa.

## O que já está no sistema de regras

Todo o núcleo de combate (atributos, Vínculo, PV, Movimentos, dano, tipos, iniciativa, Prioridade — motor de turno em seleção simultânea + resolução manual em lote (Cap. 86): todo mundo escolhe a própria ação ao mesmo tempo, sem "vez" sequencial nem negociação de Prioridade nenhuma, e o Mestre resolve a Rodada na ordem certa (não-Ataque sempre antes de Ataque; entre Ataques, Prioridade decide antes de Iniciativa) clicando "▶️ Avançar" um Pokémon por vez, sem timer nenhum — e os Movimentos de carregar 2 turnos (Cap. 25, Solar Beam e companhia) —, condições de status — Paralisia/Sono/Congelamento/Confusão testados sozinhos, dano de status por turno automático, Magic Guard bloqueando qualquer PV indireto de forma consistente —, Recuo/Dreno/Movimentos de cura na porcentagem oficial, Movimentos que trocam de campo depois de atacar, Desmaio pedindo o próximo Pokémon e vitória automática quando um Time inteiro cai), a progressão de Nível por batalhas vencidas, a Pokédex completa (Gen 1–9) e o banco de Movimentos oficiais (cada um com descrição em português), a organização de Equipe/Banco por arrastar, o fluxo guiado de entrada na Arena (Time → Soltura em segredo → Revelação simultânea, Cap. 17/55), e uma Mochila de itens por Treinador (gerenciada pelo Mestre) organizada em 5 abas com tabela (Poções e Berries, Pokébolas, Itens de Missão, TM, Inventário Geral), com o catálogo oficial completo por categoria (`ITEM_DEX`, 417 itens em 11 categorias — incluindo as 229 TMs vigentes de Scarlet/Violet, sempre disponível por inteiro), cada item com descrição em português (item de cura já citando o valor real do sistema, não o oficial do jogo) que autocompleta sozinha ao ser escolhido — "+ Adicionar" é só escolher da lista e clicar, sem campo nenhum pra preencher na mão. Um botão **"▶️ Usar"** em cada linha (pro dono da ficha ou o Mestre) pula direto pra escolher o Pokémon certo pra aquele item, sem precisar abrir a Cura e achar o item de novo lá. Cinco tipos de item têm efeito de verdade: cura de PV, de Condição/Confusão e reanimação de desmaiado (Vida/Condição/Reviver/Ambos, com a trava de que só Reviver funciona em quem está desmaiado) e recuperação/aumento de PP (Ether/Max Ether/Elixir/Max Elixir/PP Up/PP Max) — fora de batalha na aba Cura ou dentro da Arena; um sexto tipo, Outro (Pokébolas, pedras, TMs etc.), segue o mesmo fluxo de escolher o Pokémon mas ainda sem efeito mecânico de verdade (Cap. 25).
