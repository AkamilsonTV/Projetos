# Pokémon RPG — Diário de Treinador

- **Regras** (livro consolidado, v0.2): [`regras.md`](regras.md)
- **Código-fonte do site**: [`site/diario-de-treinador.html`](site/diario-de-treinador.html)
- **Site publicado**: veja a seção [Publicar no GitHub Pages](#publicar-no-github-pages-uma-vez) abaixo — depois de ativado, o link fica em `https://<seu-usuário>.github.io/<repositório>/`.

O site é uma página HTML única, hospedada de graça no **GitHub Pages**, com os dados (fichas de todo mundo) salvos em tempo real num banco **Firebase Firestore** (também grátis, sem cartão de crédito). Sem esse banco configurado, o site abre mas mostra uma tela avisando que falta ligar o banco de dados.

## Visual e sprites

O tema é mais "jogo" que "wiki": fundo em tom pergaminho, cantos arredondados, títulos numa fonte pixelada (Press Start 2P) e badges de Tipo em formato de pílula. Cada Pokémon na ficha mostra automaticamente o sprite pixelado oficial da espécie (via [PokeAPI/sprites](https://github.com/PokeAPI/sprites), puxado pelo número da Pokédex salvo quando a Espécie é preenchida) — sem espécie definida, mostra um "❔" no lugar.

## Regras e guias dentro do site

O botão **"📖 Regras"** (no topo, em qualquer tela) abre três sub-abas, cada uma buscando o `.md` correspondente direto deste repositório — não são cópias coladas no site:

- **📜 Regras** — [`regras.md`](regras.md), o livro de regras.
- **🎒 Guia do Treinador** — [`guia-treinador.md`](guia-treinador.md), passo a passo de uso pra quem joga: desde entrar/criar personagem até cada função da própria ficha (tema claro/escuro incluso).
- **🛠️ Guia do Mestre** — [`guia-mestre.md`](guia-mestre.md), o mesmo tipo de passo a passo, mas das funções exclusivas do Mestre.

Como nenhum desses é uma cópia colada no HTML: sempre que a gente atualizar qualquer um dos três arquivos e enviar o commit, a próxima vez que alguém abrir aquela aba no site já vê a versão nova, sem precisar tocar no código. **Toda função nova do site precisa ganhar uma explicação nesses guias** — ao contrário do livro de regras (que só existe pra descrever o sistema em si), os guias existem pra ensinar a usar o que já está em vigor no site, então não podem ficar desatualizados. Funciona antes mesmo de configurar o Firebase.

## Como usar o site

- **Mestre**: define um PIN na primeira vez que entrar em "Sou o Mestre"; depois disso, usa esse mesmo PIN pra sempre. Vê e edita a ficha de todos os Treinadores da mesa, incluindo Nível e Vínculo (que os jogadores só enxergam, não editam) e o contador de batalhas vencidas (visível só pro Mestre).
- **Treinador**: cria a própria ficha (nome + PIN) em "Sou Treinador → Criar personagem"; depois entra de novo com nome + PIN. Pode ativar "Compartilhar com a mesa" pra deixar outros Treinadores verem a própria ficha (somente leitura).

### Progressão de Nível

A cada 4 batalhas vencidas (contador que só o Mestre vê e mexe), o Treinador sobe 1 Nível automaticamente e o contador zera. Ver [`regras.md`](regras.md#24-progressão-de-nível) para detalhes.

## Configurar o banco de dados (Firebase) — uma vez só

1. Acesse [console.firebase.google.com](https://console.firebase.google.com/) e entre com uma conta Google.
2. **Criar projeto** → dê um nome qualquer (ex: `diario-de-treinador`) → pode desativar o Google Analytics → **Criar projeto**.
3. No menu lateral, vá em **Compilação → Firestore Database** → **Criar banco de dados** → escolha um local (qualquer um serve) → inicie em **modo de teste** (ajustamos as regras de acesso no passo 6).
4. Ainda no console, clique no ícone de engrenagem (⚙️) → **Configurações do projeto**. Na aba **Geral**, role até "Seus apps" → clique no ícone **`</>`** (Web) → dê um apelido ao app → **Registrar app**.
5. O Firebase vai mostrar um bloco `firebaseConfig` parecido com este:
   ```js
   const firebaseConfig = {
     apiKey: "AIzaSy...",
     authDomain: "diario-de-treinador.firebaseapp.com",
     projectId: "diario-de-treinador",
     storageBucket: "diario-de-treinador.appspot.com",
     messagingSenderId: "123456789",
     appId: "1:123456789:web:abcdef"
   };
   ```
   Copie esses 6 valores e cole-os no arquivo [`site/diario-de-treinador.html`](site/diario-de-treinador.html), substituindo o bloco `FIREBASE_CONFIG` no topo do `<script>` (procure por `COLE_AQUI`). Depois salve, faça commit e push.
6. **Regras de segurança do Firestore** — no console, vá em **Firestore Database → Regras** e cole exatamente isto (restringe leitura/escrita a só esse documento do jogo, e bloqueia qualquer outra coisa no banco):
   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /diario/estado {
         allow read, write: if true;
       }
       match /{document=**} {
         allow read, write: if false;
       }
     }
   }
   ```
   Clique em **Publicar**.

Pronto — depois disso, qualquer pessoa que abrir o site (em qualquer aparelho) lê e escreve no mesmo banco em tempo real: o que um jogador edita aparece pros outros sem precisar recarregar a página.

## Instalar como app (PC, Mac, Linux, Android)

O site já é um **PWA** (Progressive Web App) — dá pra "instalar" ele como se fosse um programa de verdade, com janela própria, ícone na área de trabalho/barra de tarefas e sem a barra de endereço do navegador, sem precisar baixar nem instalar nada separado:

1. Abra o link do Diário de Treinador (o de `.../pokemon-rpg/site/diario-de-treinador.html`) no **Chrome** ou **Edge**.
2. Clique no ícone de instalação que aparece do lado direito da barra de endereço (um monitor com uma setinha) — ou no menu **⋮ → Salvar e compartilhar → Instalar app "Diário de Treinador"**.
3. Pronto — abre uma janela própria, com a Pokébola como ícone, e um atalho fica salvo (Menu Iniciar/Launchpad/gaveta de apps, dependendo do sistema).

**Ele sempre mostra a versão mais nova do site — não é uma cópia.** A "instalação" só cria um atalho que abre a mesma página ao vivo, então qualquer atualização publicada aqui (Movimento corrigido, regra nova, o que for) já aparece sozinha na próxima vez que abrir o app — e os dados do jogo continuam sincronizando em tempo real pelo Firebase do jeito de sempre, exatamente como no navegador comum. Não tem passo de "atualizar o app": não existe uma versão separada pra atualizar.

Tecnicamente, isso é um `manifest.webmanifest` (nome, ícone, cor do tema) + um Service Worker mínimo (`sw.js`, só existe pra habilitar o botão "Instalar" — não guarda cache de nada, então nunca serve uma versão velha) — os dois arquivos moram do lado do `diario-de-treinador.html`, dentro de `pokemon-rpg/site/`.

## Sincronização entre aparelhos

Sim: os dados do jogo (fichas, PINs, Vínculo, Nível, batalhas etc.) ficam salvos no Firebase, não no navegador — então editar no celular aparece no PC e vice-versa, em tempo real. Só duas coisas ficam presas a cada aparelho, por conveniência, e nunca afetam os dados do jogo: se você está logado (pra não pedir PIN toda hora) e quais fichas estão abertas/fechadas na tela.

## Segurança

Os PINs ficam guardados em texto simples no banco de dados. É uma trava social para o grupo, não um cofre: alguém com acesso técnico ao banco (ou ao link, se as regras de segurança não estiverem configuradas como acima) consegue ver os dados de todo mundo. Não reutilize senhas importantes como PIN aqui.

## Quem edita o quê

- **Mestre**: quem "coloca o Pokémon na ficha" — Espécie, Tipo 1/2, Atributos Naturais e os 4 Movimentos de qualquer Treinador da mesa, além de adicionar/remover Pokémon do time de alguém. Também é o único que edita Estágios e PP (Atual/Máximo) diretamente.
- **Treinador**: cuida do dia a dia da própria ficha — Apelido, PV atual, Condição/Confuso, e **reorganizar os próprios Pokémon** entre Equipe e Banco (ver abaixo). Estágios e PP mudam sozinhos pelo sistema (Movimento usado, item, saída de campo), sem edição direta do jogador. Não escolhe qual Pokémon entra na ficha — isso é só do Mestre.

## Pokédex completa (Gen 1–9) e banco de Movimentos

O site já vem com **todos os 1025 Pokémon** (espécie base de cada um, sem formas regionais/Mega/Gigantamax) e **847 Movimentos oficiais** embutidos — tipos, categoria e Base Stats/Poder/Precisão/Prioridade/**PP** reais, convertidos pelas tabelas das regras (Cap. 6.1 para Atributos, Cap. 9 para Poder de Movimento, Cap. 8.6 para PP). Fonte dos dados: [PokeAPI](https://pokeapi.co/).

- **Espécie** (só o Mestre vê o campo): digite o nome em inglês, como no jogo — assim que bater com um da base, Tipo 1/2 e os seis Atributos Naturais são preenchidos sozinhos, sem precisar clicar em nada.
- **Movimentos, Mestre**: campo "nome" livre com autocomplete, sem restrição (pode digitar qualquer um dos 847) — preenche Tipo/Categoria/Poder/Precisão/Prioridade/Efeito sozinho e continua editável na mão. Movimentos de poder fixo/variável (Seismic Toss, Dragon Rage, Counter, etc.) ficam com Poder em branco — é regra em aberto (Cap. 25), o Mestre adjudica na hora.
- **Movimentos, Treinador**: escolhe os próprios 4 Movimentos, mas restrito ao que a espécie realmente pode aprender — uma barra "Learnset" horizontal por slot, acima da mini-tabela dele, com quatro opções (**Nível** = aprendizado natural, só até o teto liberado pelo Nível do Treinador (Cap. 8.2/8.4); **Evo** = ganho ao evoluir pra essa forma; **TM** = só o que a espécie aprende por Fita, sem depender de Nível; **Egg** = só o que a espécie aprende por Breeding). Os dados de aprendizado (learnset) também vêm do PokeAPI. Não existe opção de HM — a mecânica saiu dos jogos oficiais a partir da Geração 9.
- Z-Moves e Movimentos Dynamax/Gigantamax **não** estão na base — são mecânicas de spin-off sem regra equivalente neste sistema.

## Equipe e Banco (arrastar Pokémon)

Cada Treinador tem 6 posições de **Equipe** (os Pokémon ativos) e um **Banco** sem limite (menu deslizante — botão "🗃️ Banco (N)" abre/fecha). O próprio Treinador (ou o Mestre) reorganiza arrastando pela alcinha **⠿** no canto do card — só isso: quem decide qual Pokémon existe e o que ele é continua sendo o Mestre.

- Arraste um Pokémon do Banco pra um slot vazio da Equipe → ele entra no time.
- Arraste um Pokémon do Banco pra cima de um Pokémon já ativo → eles trocam de lugar (o ativo vai pro Banco).
- Arraste dentro da própria Equipe (ou dentro do próprio Banco) → troca as posições dos dois.
- Arraste um Pokémon ativo pra dentro do Banco (área vazia do menu) → ele sai da Equipe e vai pro Banco.

Funciona com mouse e com toque (celular).

## Arena (esboço v1 + motor de ataque)

Botão **"🏟️ Arena"** no topo — espaço à parte pra montar uma batalha, feito como primeiro rascunho pra iterar em cima. Modelo de dados novo em `STATE.arena` (`teams` + `entries` + `lastRoll` + `log` + `round`), migração automática pra fichas salvas antes disso existir.

- **Times**: sem limite, criados/renomeados/removidos só pelo Mestre — não precisa ser 1×1, dá pra ter quantos Times a mesa quiser.
- Cada Treinador arrasta (pelo ⠿, mesma engine de Pointer Events da Equipe/Banco) um Pokémon da própria Equipe ativa pra dentro de um Time. A entrada guarda só a referência (Treinador + Pokémon) — o Pokémon continua na ficha normalmente, nada é duplicado ou movido de lá.
- **Equipe ativa é pública, mas cada Pokémon começa em Pokébola**: `arenaSourceHTML()` renderiza o card "Equipe ativa" de **todos** os Treinadores (`STATE.trainers.map(arenaTrainerSourceHTML)`) pra qualquer viewer, jogador ou Mestre — os cards de todo mundo aparecem sempre. Mas cada Pokémon nele só mostra sprite/nome de verdade pra quem for `canControl` (dono ou `SESSION.role==='gm'`) OU já tiver `p.arenaRevelado===true`; pra qualquer outro viewer, vira um tile Pokébola (`arena-source-tile-hidden`) até o Pokémon ir pra um Time pela primeira vez. Controle (`drag-handle`, `arena-source-tile-swappable`) segue restrito a `canControl` do mesmo jeito.
- **Dentro de um Time, revelado é `true` por padrão** (`DT.arenaSetEntry`/arrastar, `DT.arenaSwapIn`/Trocar): um Pokémon aparece pra mesa inteira (sprite, `arenaEntryHTML`) assim que entra por esses dois caminhos, mesmo antes de agir — persistido no próprio Pokémon (`p.arenaRevelado`), então mesmo saindo do Time depois, ele já aparece de verdade na Equipe ativa dali em diante, **pelo resto dessa mesma passagem pela Arena** (`p.arenaRevelado` zera ao sair de vez — `DT.arenaLeave` — ver bullet abaixo; sem esse reset, um Pokémon que já lutou uma vez ficava marcado como revelado pra sempre, vazando o roster inteiro do Treinador em toda Soltura futura). **Exceção**: uma entrada criada por `DT.arenaPickLead` (Soltura, ver bullet dedicado abaixo) nasce com `revelado:false` de propósito — fica em Pokébola até `DT.arenaRevelarTodos`. `migrateState()` **não** força mais essas a `true` (removida a migração antiga que fazia isso — ela existia de quando toda entrada nascia revelada; hoje `revelado:false` é um estado normal e esperado).
- **Iniciativa (Cap. 16, revisado) + trava de turno**: o Mestre clica "▶️ Iniciar Batalha" e o site calcula sozinho quem age primeiro (Velocidade Efetiva → Natural → 1d6 em empate, com o −10 de Paralisia do Cap. 20.4 já aplicado, e excluindo entradas com `revelado:false`) entre quem está em campo, mostra a fila com quem está com a vez destacado (`STATE.arena.round`), e avança sozinha quando quem está com a vez ataca. `advanceRoundPastFainted(r)` — chamada em todo ponto que mexe em `r.currentIdx` — agora também detecta quando `r` esgota (`r.currentIdx>=r.order.length`) e, se `r===STATE.arena.round` (a Rodada corrente de verdade, não uma local ainda não publicada) e a batalha não foi vencida, já calcula a PRÓXIMA Rodada sozinha (`computeInitiativeOrder()` de novo, `number+1`, `currentIdx:0`) e substitui `STATE.arena.round` — só precisa "Iniciar Batalha" uma vez; "🔁 Recalcular" continua disponível pro Mestre forçar manualmente. `arenaInsertIntoActiveRound(entryId)` cobre a entrada de surpresa: com uma Rodada ativa, calcula a Velocidade Efetiva do recém-chegado e o insere em `r.order`/`r.meta` na primeira posição a partir de `r.currentIdx` onde a Velocidade dele supere a de quem está lá — nunca antes de `r.currentIdx` (quem já agiu fica intocado). Chamada em `DT.arenaSetEntry` (novo participante) e em `DT.arenaSwapIn` quando a troca NÃO é a própria vez de ninguém (`!wasCurrent` — reposição forçada por desmaio, Cap. 59); numa troca voluntária (`wasCurrent`), o entrante continua esperando a Rodada seguinte, como sempre foi. Com uma Rodada ativa, `DT.arenaSelectActor` só libera agir pra `currentRoundEntryId()===entryId` (jogador) — `SESSION.role==='gm'` sempre passa, fora de ordem, é quem adjudica a negociação de Prioridade (Cap. 17) ao vivo. Sem Rodada ativa, continua liberado pra todo mundo.
- **Ação de verdade — clicar no Pokémon, sem botões separados**: não existe mais "Usar" nem "Atacar"/"Agir" como botões próprios — clicar direto no card de um Pokémon num Time (já visível desde que entrou lá) e vivo (`DT.arenaSelectActor`) abre um popup (`arenaActionPanelHTML`, `.arena-action-overlay`/`.arena-action-overlay-card`) com um menu de quatro opções: **Atacar**, **Usar Item**, **Trocar de Pokémon**, **Fugir** (`SESSION.arenaAction`). Antes era um `.card` fixo no fluxo normal da página (precisava rolar até ele, e de novo até o alvo/tile de troca lá em cima); agora é um popup centralizado, maior, que de cara já mostra quem está em campo, **lado a lado, um bloco por Time** (`arenaActionBattlefieldHTML`, `.arena-action-battlefield`/`.arena-action-team-col` — um `<div>` por `STATE.arena.teams`, cada um listando as próprias entries via `arenaEntryHTML` de novo, o mesmo card que já existe no campo de batalha, então a lógica de clique/elegibilidade E o gatilho **"📊"** de abrir o painel de Atributos não são duplicados em lugar nenhum). Quando um Movimento/Item pede um alvo manual, é a própria `arenaEntryHTML` de cada entry (já calculada como `arena-slot-targetable`, via a mesma checagem `pickingTarget`/`eligibleMoveTargets`/`eligibleItemTargets` que o campo de batalha normal usa) que fica clicável ali dentro do popup — sem uma "grade de alvos" separada, é literalmente clicar em quem já está no campo mostrado. Trocar reaproveita `arenaSourceTilesRowHTML(t)` (fatorada de `arenaTrainerSourceHTML`, que agora só chama essa função pros próprios tiles) num bloco à parte pra quem NÃO está em campo (Equipe ativa). Se o Pokémon estiver Confuso, o teste da Confusão (ver abaixo) roda automaticamente antes desse popup abrir. Escolhendo Atacar, aí sim se escolhe o Movimento; o alvo (se precisar de um) vem depois. O motor resolve a Precisão (Cap. 10, com fallback automático pra sempre-acerta em Movimentos sem Precisão definida — inclusive corrigindo fichas salvas de antes dessa checagem existir, via `migratePokemonMoves`), Crítico (Cap. 11), Dano (Cap. 12) e Tipos (Cap. 13) com 1d6, e o Efeito Percentual (Cap. 14) com 1d10 quando o Movimento tiver um efeito de status conhecido — se aplicar, a Condição já entra sozinha na ficha do alvo, respeitando a regra de nunca empilhar duas Condições Principais (Confusão é a exceção, Cap. 20). PV chegando a 0 marca Desmaio (Cap. 19) automaticamente. **Card da Arena mais respirado**: `.arena-slot` ganhou mais largura/espaçamento (78px→84px, gap 12px→16px entre cards) — o aviso **"😵 Escolher próximo"** (Cap. 25/59, texto comprido) saiu de `.arena-turn-badge` (`position:absolute`, pensado pro rótulo curto "▶ Turno" — flutuando por cima acabava cobrindo o PV e a sprite por baixo, reportado com print) e ganhou a própria classe `.arena-fainted-banner`, no fluxo normal do card (não flutua, empurra o resto pra baixo em vez de sobrepor).
- **Popup de Ação e quadro de dado, na mesma janela**: quando o Movimento resolvido de verdade gera uma rolagem (`STATE.arena.lastRoll`), o popup de Ação NÃO fecha mais na hora — `SESSION.arenaResolving=true` mantém ele aberto, mas congelado (`arenaActionPanelHTML` troca pra uma view só com o campo de batalha e um "🎲 Resolvendo…", sem menu/Cancelar/✕; `arenaEntryHTML` reforça por conta própria que nenhum card fica clicável nesse meio-tempo, e todo `DT.arena*` de início de ação tem um `if(SESSION.arenaResolving) return;` de defesa em profundidade) enquanto o `#diceOverlay` anima por cima dele (mesmo fundo escurecido — `.arena-action-overlay-resolving` fica com fundo transparente pra não escurecer em dobro por baixo do fundo do próprio quadro de dado). Antes, `arenaResetActionState()` rodava de forma síncrona ANTES do `render()` que abre o quadro de dado — o popup de Ação sumia e um quadro bem menor (360px vs. 560px) aparecia do zero por cima, com o próprio fade-in reiniciando, dando a sensação de "outra janela" mesmo os dois DOM sendo trocados no mesmo tick JS (reportado como "tem que aparecer na mesma camada"). Agora `arenaFinishRoll()` (chamada tanto no fim natural da animação, dentro de `startDiceRollAnimation`, quanto num `DT.dismissRoll()` clicado no meio do caminho) é quem de fato zera `DICE_ROLL_ANIM` e chama `arenaResetActionState()` — sempre no MESMO `render()` que revela o resultado, então o popup só fecha quando o quadro de dado já assentou de vez. O ramo de troca forçada por U-turn/Volt Switch/Parting Shot (`SWITCH_OUT_MOVES`) continua fora dessa trava — ele já deixava o popup aberto por design próprio, trocando pra tela de Trocar, então o dado anima por cima dele do mesmo jeito, sem precisar de `arenaResolving`.
- **Alvo do Movimento (Cap. 8.5)**: cada Movimento respeita sua própria lógica de alvo, vinda do dado oficial (`MOVE_TARGETS`, gerado do `target_id` do PokeAPI) — um Movimento **em si mesmo** (Swords Dance, Rest) resolve na hora, sem pedir clique; um **só aliado** (Helping Hand) ou **só inimigo** (Counter) só deixa clicar em quem for elegível daquele time (`eligibleMoveTargets`); um **de área** (Earthquake, Discharge — categoria `all-other`) atinge sozinho todo mundo daquela categoria de uma vez, podendo incluir aliados do próprio atacante junto com os inimigos; um **de campo** (Stealth Rock) resolve sem calcular dano, só registra o uso (mecânica ainda em aberto, Cap. 25). Pra Movimentos de área, a Precisão/Crítico/Efeito Percentual são **uma rolagem só pro uso inteiro** (mesmo d6/1d10 compartilhado, `resolveMoveUse`), só o Dano é recalculado por alvo — mas se o efeito pega ou não em cada um ainda respeita o Cap. 20 individualmente (um alvo que já tinha Condição não recebe outra, mesmo com a rolagem batendo).
- **Paralisia/Sono/Congelamento automáticos (Cap. 20.4/21/22)**: antes do menu de ação abrir, `arenaStatusActionPreCheck` já testa sozinho quem estiver com uma dessas três — Paralisia (1d6, 1–2 perde a ação), Congelamento (1d6, 1–4 continua, 5–6 descongela e libera o menu no mesmo turno), Sono (1º turno obrigatório sem rolar nada, 2º–3º com 1d6, 5–6 acorda, e acorda garantido depois do 3º turno testado sem rolar de novo — contagem em `p.statusTurns`, mesmo campo do contador de Veneno Grave, nunca usados ao mesmo tempo). Mostra um aviso + log; se perder a ação, o turno avança sozinho (`arenaAdvanceTurn`) sem abrir o menu. Qualquer golpe do Tipo Fogo que acerte com dano descongela na hora (`applyAttackResult`), sem precisar bater com o nome do Movimento.
- **Confusão automática (Cap. 23)**, resolvida logo depois das três acima (mesma ordem do Cap. 24): `arenaConfusionPreCheck` já rola sozinho o 1d6 pra tentar eliminar a Confusão (5–6 termina) e, se continuar, o 1d6 do efeito (1–2 perde a ação e sofre 1 PV — bloqueado se tiver Magic Guard, mas ainda perde a ação; 3–6 age normalmente) — mostra um aviso com os dois resultados e registra no log. Se a ação for perdida, o turno já avança sozinho sem abrir o menu.
- **Recuo, Dreno e Movimentos de cura (Cap. 25)**: `applyMoveSelfHealEffects` (chamado de `resolveMoveUse`, depois de `applyAttackResult`/`applyAbilityHooksAfterHit`) lê três tabelas curadas com o dado oficial da PokeAPI (`meta.drain`/`meta.healing`) — `MOVE_RECOIL` (11 Movimentos, % do dano causado tirado do próprio atacante), `MOVE_DRAIN` (11 Movimentos, % do dano causado curado no atacante — vira dano nele em vez de cura se o alvo tiver Liquid Ooze) e `MOVE_HEAL` (15 Movimentos incluindo Rest, % do PV Máximo de quem for o alvo resolvido do golpe). Magic Guard bloqueia o recuo e o dano invertido de Liquid Ooze (dano indireto no próprio atacante), sem bloquear a cura em si. Rest (`MOVE_EFFECTS['Rest']`, curado à mão — a PokeAPI não marca ele com nenhum ailment) cura qualquer Condição anterior antes de aplicar o próprio sono, e cura 100% do PV via `MOVE_HEAL`.

- **Overlay de dado**: todo mundo conectado vê um quadro no centro da tela com o resultado (`STATE.arena.lastRoll`), numa div própria fora da árvore da ficha pra não recriar sprite nenhum a cada quadro da animação. O **d6** gira e assenta primeiro; só então, se houver Efeito Percentual, o **1d10** gira e assenta (com uma 2ª tentativa em sequência se veio Crítico e a 1ª falhou) — um dado de cada vez, nunca simultâneos. Some sozinho depois de alguns segundos. Uma rolagem só dispara esse overlay se aconteceu há pouco (`DICE_FRESH_MS`, 8s) — corrige um bug do v1 em que reabrir/recarregar a página replicava o overlay pra um ataque antigo já salvo no banco.
- **Registro**: `arenaLogHTML()` guarda as últimas 40 linhas de ataque/status/troca/item resolvidas (`STATE.arena.log`), rolável, com botão "Limpar" pro Mestre. A entrada mais nova só aparece ali depois que o dado dela termina de girar no overlay, pra não entregar o resultado antes da hora. Janela flutuante (`.arena-log-panel`), arrastável pela barra do topo e redimensionável pelo cantinho `.arena-log-resize-handle` — mesmo motor de arraste da `.arena-stats-panel` (offset do ponteiro, mexe direto no `style.left/top` fora do ciclo de `render()`), com um motor irmão de resize (`LOG_RESIZE`) que pina o painel em `left/top` explícitos assim que o resize começa (senão a borda ancorada por `bottom`/`right` do CSS padrão se deslocaria sozinha crescendo). Posição (`SESSION.arenaLogPos`) e tamanho (`SESSION.arenaLogSize`) são só locais, por viewer, nunca sincronizam — igual ao painel de atributos.
- **Indicativo visual de Estágio (Cap. 15.1)**: `stageBadgesHTML(poke)` desenha uma etiqueta tipo "Atq +1"/"Vel -2" (`.stage-badge-up` verde/`.stage-badge-down` vermelha) por Atributo com `poke.estagios[stat]!==0`, embaixo de qualquer card revelado na Arena (`arenaEntryHTML`) — cobre os 5 Atributos normais mais Precisão/Evasão, sempre lendo o Estágio real (o mesmo que já alimentava `effectiveStat`/o motor de ataque; só faltava aparecer em algum lugar durante a própria batalha).
- **📊 Painel flutuante de atributos**: botão `.arena-info-btn` em todo card revelado (`arenaEntryHTML`) chama `DT.arenaStatsShow(entryId)`, que empurra `entryId` pra `SESSION.arenaStatsOpen` (array — refazendo a mesma checagem de `canSeeReal` — GM, dono ou já revelado — e sem duplicar se já estiver aberto) e dispara `arenaStatsPanelHTML()`, que mapeia CADA entryId aberto pra um painel via `arenaStatsOnePanelHTML(entryId, idx)`: Tipo, PV atual/máximo, Condição/Confuso, Habilidade (com o efeito como legenda), Natureza e uma tabela Atributo/Estágio/Efetivo calculada com o `effectiveStat(t,p,stat)` de verdade (mesma função que a batalha usa), mais os Movimentos com PP restante. Dá pra ter **vários painéis abertos ao mesmo tempo, de Pokémon diferentes** — cada `<div class="arena-stats-panel" data-entry-id="...">` carrega o próprio id, e `DT.arenaStatsClose(entryId)` fecha só aquele, sem mexer nos outros. Sem posição arrastada salva ainda, cada painel nasce em cascata (`top:70+idx*36px; right:16+idx*20px`) pra não empilhar exatamente um em cima do outro. **Arrastável**: `onpointerdown="DT.arenaStatsDragStart(event)"` na barra do topo do painel liga um motor de arraste próprio e simples (`STATS_DRAG` + `DT._statsDragMove`/`DT._statsDragEnd`, mexendo direto em `style.left/top` fora do ciclo de `render()` enquanto arrasta, lendo `data-entry-id` do painel pra saber em qual chave gravar a posição final só no soltar) — sem ghost nem drop-target, diferente do `DRAG` usado pra arrastar Pokémon entre Equipe/Banco/Time. Tudo isso vive só em `SESSION` (`arenaStatsOpen` — array de entryId; `arenaStatsPos` — mapa entryId→{x,y}), que **nunca sincroniza** com o Firestore — cada pessoa na mesa abre, arrasta e fecha os próprios painéis sem afetar os outros. O botão `.arena-stats-close` (✕) e o "Limpar" do Registro (`.arena-log-panel`) carregam `onpointerdown="event.stopPropagation()"` além do próprio `onclick` — sem isso, o `pointerdown` do clique borbulha primeiro pra barra do topo, cujo handler chama `preventDefault()`+`setPointerCapture()` (pra iniciar o arraste); isso desvia o `mousedown`/`mouseup` sintetizados pro elemento que capturou o ponteiro, e o "click" do navegador acaba disparando na BARRA em vez de no botão — o `onclick` do botão nunca roda (bug relatado: "clico e não fecha").
- **Negociação de Prioridade (Cap. 17.1-17.3)**: `findBestPriorityReaction(attackerEntry, usedPriority)` percorre `round.order` procurando, entre quem ainda não agiu na Rodada (`arenaEntryAindaNaoAgiu` — índice na fila ainda não alcançado pelo `currentIdx` E `entry.prioAgiuRodada` diferente do `round.number`) e é de um `teamId` diferente do atacante, o melhor Movimento (maior Prioridade, com PP) que exceda estritamente a Prioridade usada (empate não conta, 17.3). `arenaMaybePausePriority(atkEntry, move, category, manualTargetIds, isChargeRelease)` roda isso **ANTES** de qualquer Movimento resolver (chamado nos 3 pontos que estavam prestes a chamar `DT.resolveArenaMove` de verdade: `DT.arenaPickMove` pro self/área, `DT.arenaSelectTarget` pro alvo manual, e o ramo de soltar carga em `DT.arenaSelectActor`) — se achar reação, PAUSA ali mesmo (nenhum dado rola ainda) guardando `STATE.arena.priorityPending` (a pergunta) e `STATE.arena.priorityPausedAction = {entryId,moveIdx,moveName,category,manualTargetIds,isChargeRelease}` (a ação original em espera) e devolve `true` pro chamador não resolver nada agora; `DT.resolveArenaMove` em si não faz mais nenhuma checagem de Prioridade internamente — só resolve de vez o que mandarem. Sincronizado — todo mundo na mesa vê o mesmo popup (`arenaPriorityPromptHTML()`, `.priority-overlay`/`.priority-overlay-card`), mas só o dono ou o Mestre veem a pergunta de verdade com os botões Sim/Não; o resto vê um popup genérico "Verificando prioridade, aguarde." sem nome/Movimento nenhum. Enquanto tiver uma pergunta pendente, `DT.arenaSelectActor` recusa abrir o menu de ação pra qualquer entrada. `DT.arenaPriorityAnswer('sim'|'não')` sempre termina chamando `arenaResumePausedAction(chainFrom)`: "não" (ou perder a ação por Status/Confusão, ou Movimento mudado, ou sem alvo) chama sem `chainFrom` — não tenta encadear mais nada (senão reabriria a mesma pergunta que acabou de recusar, já que recusar não marca `prioAgiuRodada`), só finaliza `priorityPausedAction` de vez via `DT.resolveArenaMove` de novo; "sim" marca `entry.prioAgiuRodada = round.number` (ANTES de resolver, mesmo que a ação se perca a seguir), roda os mesmos `arenaStatusActionPreCheck`/`arenaConfusionPreCheck` de sempre, escolhe o alvo (self/área resolvem frescos via `eligibleMoveTargets`; Movimento de alvo manual mira por padrão em `vsAttackerEntryId` — quem provocou a reação — caindo pro 1º elegível que sobrar, ou fracassando sem efeito se não sobrar ninguém), chama `DT.resolveArenaMove` pra valer, e SÓ ENTÃO chama `arenaResumePausedAction({entryId,prioridade,moveName})` com o REATOR que acabou de agir como referência — é isso que permite a cadeia (Prioridade ainda maior do lado OPOSTO AO REATOR, não ao atacante original, reagindo por sua vez) sem cair num laço com quem acabou de recusar, e sempre termina porque cada reação aceita tira aquele Pokémon do grupo de "ainda não agiu" pelo resto da Rodada. Quando não sobra mais ninguém pra perguntar (com ou sem `chainFrom`), `arenaResumePausedAction` finalmente resolve `priorityPausedAction` (o ataque do jogador da vez, que ficou esperando esse tempo todo) via `DT.resolveArenaMove`, se quem ia agir ainda existir/estiver vivo/com o mesmo Movimento. `advanceRoundPastFainted` também pula quem já tem `prioAgiuRodada===round.number` quando o ponteiro normal da fila chega nele (mesmo padrão de pular quem desmaiou) — a vez dele já foi usada, sem perguntar de novo. `DT.arenaStartRound`/`DT.arenaEndRound` limpam `priorityPending` e `priorityPausedAction` como defesa em profundidade.
- O que fica de fora, por enquanto: Movimentos de campo (Stealth Rock, clima), Baton Pass, Jungle Healing/Purify, e o efeito mecânico de verdade dos itens catalogados como `'outro'` (Pokébolas, Itens de Batalha/Evolução/Segurados, Itens-Chave, TMs) — isso continua com o Mestre.

## O que já está no sistema de regras

Todo o núcleo de combate (atributos, Vínculo, PV, Movimentos, dano, tipos, iniciativa, Prioridade — incluindo a trava de turno que só libera quem está na vez, com o Mestre podendo agir por qualquer um fora de ordem, a negociação automática de Prioridade (Cap. 17.1-17.3, pergunta Sim/Não pra quem tem Movimento de Prioridade maior que o que acabou de ser usado) e os Movimentos de carregar 2 turnos (Cap. 25, Solar Beam e companhia) —, condições de status — Paralisia/Sono/Congelamento/Confusão testados sozinhos, dano de status por turno automático, Magic Guard bloqueando qualquer PV indireto de forma consistente —, Recuo/Dreno/Movimentos de cura na porcentagem oficial, Movimentos que trocam de campo depois de atacar, Desmaio pedindo o próximo Pokémon e vitória automática quando um Time inteiro cai), a progressão de Nível por batalhas vencidas, a Pokédex completa (Gen 1–9) e o banco de Movimentos oficiais (cada um com descrição em português), a organização de Equipe/Banco por arrastar, o fluxo guiado de entrada na Arena (Time → Soltura em segredo → Revelação simultânea, Cap. 17/55), e uma Mochila de itens por Treinador (gerenciada pelo Mestre) organizada em 5 abas com tabela (Poções e Berries, Pokébolas, Itens de Missão, TM, Inventário Geral), com o catálogo oficial completo por categoria (`ITEM_DEX`, 417 itens em 11 categorias — incluindo as 229 TMs vigentes de Scarlet/Violet, sempre disponível por inteiro), cada item com descrição em português (item de cura já citando o valor real do sistema, não o oficial do jogo) que autocompleta sozinha ao ser escolhido — "+ Adicionar" é só escolher da lista e clicar, sem campo nenhum pra preencher na mão. Um botão **"▶️ Usar"** em cada linha (pro dono da ficha ou o Mestre) pula direto pra escolher o Pokémon certo pra aquele item, sem precisar abrir a Cura e achar o item de novo lá. Cinco tipos de item têm efeito de verdade: cura de PV, de Condição/Confusão e reanimação de desmaiado (Vida/Condição/Reviver/Ambos, com a trava de que só Reviver funciona em quem está desmaiado) e recuperação/aumento de PP (Ether/Max Ether/Elixir/Max Elixir/PP Up/PP Max) — fora de batalha na aba Cura ou dentro da Arena; um sexto tipo, Outro (Pokébolas, pedras, TMs etc.), segue o mesmo fluxo de escolher o Pokémon mas ainda sem efeito mecânico de verdade (Cap. 25). Também Naturezas (ajuste automático de Atributo Efetivo), Habilidades reais por espécie restritas e editáveis só pelo Mestre — 93 delas com gatilho mecânico de verdade na Arena (contra-ataque no contato, imunidade/absorção de Tipo, bônus de dano, entrada/saída de campo, fim de turno, condição espelhada, custo de PP...), as demais só texto de referência —, PP real em todos os 847 Movimentos (1 por uso, 2 contra Pressure, bloqueia em 0, **só o Mestre edita direto**) e Estágios automáticos por Movimento (dado oficial de mudança de Estágio, com as mesmas reações de Habilidade do Cap. 6.3, resetando a 0 sempre que o Pokémon sai de campo — desmaia, troca ou foge —, **também só o Mestre edita direto**). Ainda em aberto: Maturidade/Evolução definitiva, Captura, Struggle automático, clima/terreno, item equipado, Baton Pass, Jungle Healing/Purify, e efeito mecânico dos itens catalogados como `'outro'` (Pokébolas, Itens de Batalha, Itens de Evolução, Itens Segurados, Itens-Chave, TMs).
